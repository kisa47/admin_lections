Содержание лекции

Web-Серверы

Веб-сервер — это программное обеспечение, работающее на серверной стороне, которое реализует логику протокола HTTP/HTTPS. Его основная задача — принимать сетевые запросы от клиентов и отдавать им контент.
С технической точки зрения веб-сервер — это демон (служба), который:
  • Слушает определенный сетевой порт.
  • Принимает TCP-соединение (для HTTP/3 UDP из-за перехода на QUIC).
  • Парсит HTTP-сообщение (заголовки и тело).
  • Выполняет логику: либо отвечает сам, либо передает запрос другому приложению.
  • Формирует HTTP-ответ и закрывает (или удерживает Keep-Alive) соединение.

NGINX

nginx ("engine x") — это HTTP-сервер, обратный прокси сервер с поддержкой кеширования и балансировки нагрузки, TCP/UDP прокси-сервер, а также почтовый прокси-сервер.
Изначально разработан Игорем Сысоевым и распространяется под лицензией BSD из 2 пунктов.

Причины появления

В начале 2000-х годов классическая архитектура веб-серверов сталкивалась с проблемой масштабируемости. При обработке 10 000 одновременных соединений (проблема C10k) серверы тратили огромные ресурсы на переключение контекста между процессами.
В 2002 году системный администратор компании «Рамблер» Игорь Сысоев начал разработку нового веб-сервера. Главной целью было создание решения, способного эффективно обслуживать десятки тысяч одновременных соединений на одном сервере с минимальным потреблением памяти.
В 2004 году осуществлён выпуск первой публичной версии Nginx. Код был открыт, что позволило сообществу начать его доработку.

Архитектура

В отличие от традиционных веб-серверов, которые создают отдельный процесс или поток на каждое входящее соединение (как классический Apache Prefork), Nginx использует асинхронную событийно-ориентированную архитектуру. Это позволяет ему обрабатывать десятки тысяч одновременных соединений на одном ядре CPU с минимальным потреблением памяти.

Master Process (Мастер-процесс)

Это «мозг» и «дирижер» системы. Обычно запускается один раз с правами суперпользователя (root), чтобы иметь возможность занять привилегированные порты (80 для HTTP и 443 для HTTPS).
  • Чтение конфигурации: При старте или команде nginx -s reload мастер читает nginx.conf
  • Валидация: Проверяет синтаксис конфига. Если в новом конфиге ошибка, мастер просто не применит его, и старые воркеры продолжат работать. Это обеспечивает Zero Downtime (нулевой простой) при обновлениях.
  • Управление жизненным циклом: Запускает, останавливает и перезапускает Worker-процессы.
  • Сигналы: Реагирует на системные сигналы (например, SIGHUP для перезагрузки конфига, SIGQUIT для плавного завершения).
  • Привилегированные операции: Открывает слушающие сокеты (bind) и затем передает их воркерам.

Worker-процессы (Рабочие)

Это «мускулы» сервера. Именно они выполняют всю работу по сетевому взаимодействию. Запускаются без прав суперпользователя (обычно пользователь www-data или nginx). Количество задается директивой worker_processes в nginx.conf
worker_processes auto;
  • Событийный цикл (Event Loop): Каждый воркер работает в однопоточном цикле событий. Он не ждет данных. Если воркер отправил запрос к диску или базе данных, он не «засыпает», а идет обрабатывать другие готовые соединения.
  • Разделяемая память: Все воркеры используют общие структуры данных (например, кэш сессий или таблицу лимитов) через механизмы разделяемой памяти (shared memory).

Цикл обработки

  • Master читает конфиг, открывает сокет на порту 80 и форкит (создает), например, 4 Worker-процесса.
  • Workers наследуют этот открытый сокет.
  • Клиент отправляет запрос. Ядро ОС уведомляет один из свободных Worker'ов.
  • Worker читает заголовки HTTP. Если нужно прочитать файл с диска, он просит ядро сделать это и переключается на другие активные соединения.
  • Как только файл прочитан, Worker отправляет его клиенту и закрывает соединение (или оставляет открытым для Keep-Alive).

Почему это эффективно

  • Отсутствие блокировок: В Apache (Prefork) 1000 клиентов = 1000 процессов. В Nginx 1000 клиентов = 4 воркера, каждый из которых держит по 250 соединений в неблокирующем режиме.
  • Отказоустойчивость: Если Worker-процесс упадет из-за ошибки (например, в стороннем модуле), Master-процесс мгновенно создаст новый. Остальные воркеры продолжат работу.
  • Reload без простоя: Это «киллер-фича» Nginx. При nginx -s reload Master запускает новую пачку воркеров с новым конфигом. Старые воркеры завершают текущие запросы и закрываются. Пользователи даже не замечают, что конфиг изменился.

Иерархия конфигурационного файла (Контексты)

Конфигурация Nginx строится на строгой иерархии блоков, которые называются контекстами. Понимание этой вложенности критически важно: директивы работают только внутри своего контекста или наследуются в дочерние контексты.
Файл конфигурации (обычно /etc/nginx/nginx.conf) — это дерево. Если директива находится в родительском блоке, она доступна во всех дочерних, если в дочернем не указано иное.

Пример конфигурации


# 1. MAIN CONTEXT
user www-data;
worker_processes auto;

events { 
    # 2. EVENTS CONTEXT
    worker_connections 4096; 
}

http {
    # 3. HTTP CONTEXT
    include mime.types;
    sendfile on;

    # 4. SERVER CONTEXT (VHost 1)
    server {
        listen 80;
        server_name site1.com;

        # 5. LOCATION CONTEXT
        location / {
            root /var/www/site1;
        }

        location /api/ {
            proxy_pass http://backend;
        }
    }

    # 4. SERVER CONTEXT (VHost 2)
    server {
        listen 80;
        server_name site2.com;
        root /var/www/site2;
    }
}

Main (глобальный контекст)

Располагается вне каких либо блоков (корень) и задает параметры всего демона Nginx (в частности Worker`ов). На этом уровне не задаются конфигурации описывающие работу с HTTP как таковую.

# 1. MAIN CONTEXT
user                 www-data; # от имени какого пользователя работают воркеры
worker_processes     auto; # количество воркеров (обычно по числу ядер CPU).
worker_rlimit_nofile 65535; # лимит файловых дескрипторов
pid                  /run/nginx.pid; # пути к PID-файлу.
include              /etc/nginx/modules-enabled/*.conf; # вставка конфигурации из других файлов в данное место

Events

Управляет сетевым вводом-выводом. Как именно Nginx будет принимать соединения.

# 1. MAIN CONTEXT
worker_processes     auto;
...    
events { 
    # 2. EVENTS CONTEXT
    worker_connections 4096; # максимальное количество одновременных соединений на один Worker
    use epoll; # механизм уведомлений для ускорения работы в Linux системах
}

HTTP

Глобальные настройки протокола HTTP. Здесь задаются параметры, общие для всех сайтов на сервере.

# 1. MAIN CONTEXT
worker_processes     auto;
...    
http {
    # 3. HTTP CONTEXT
    include                 mime.types; # сопоставление расширений файлов и их типов.
    sendfile                on; # оптимизации передачи статических файлов напрямую из ядра ОС
    gzip                    off; # полностью отключает сжатие ответов методом gzip
    client_max_body_size    2m; # максимально допустимый размер тела HTTP-запроса
    proxy_connect_timeout   15s; # максимальное время, которое NGINX будет ждать при попытке установить TCP-соединение с проксируемым сервером
    proxy_send_timeout      10s; # максимальное время ожидания при передаче запроса к проксируемому серверу
    proxy_read_timeout      10s; # максимальное время ожидания при получении отвктаа от проксируемомого сервера
    proxy_set_header        SpaceVM-External-Ip $server_addr; # добавить заголовок к запросу при проксировании
    proxy_hide_header       Server; # Скрыть заголовок при проксировании
    ssl_protocols           TLSv1.2 TLSv1.3; # Какие типы шифрования использовать
    add_header              Referrer-Policy "no-referrer"; # Добавить заголовок в ответ
	keepalive_timeout       65; # поддерживать соединение с клиентом в секундах
    include                 /etc/nginx/sites-enabled/*; # вставка конфигурации из других файлов в данное место

    # 4. SERVER CONTEXT (VHost 1)
    server {
        ...
    }
}

Upstream

Блок upstream располагается в контексте http. Он позволяет объединить несколько физических или виртуальных серверов (бэкендов) в одну логическую группу, на которую затем ссылается директива proxy_pass.

http {
    # 3. HTTP CONTEXT
    ...
	# 1. Объявляем группу серверов (upstream)
	upstream backend_pool {
		least_conn; # Nginx отправляет запрос на тот сервер, у которого сейчас меньше всего активных соединений.
		# ip_hash; # Выбор сервера зависит от IP-адреса клиента. Один и тот же пользователь всегда будет попадать на один и тот же бэкенд.
		# Алгоритм по умолчанию - Round Robin
		server 127.0.0.1:8001 weight=1 max_fails=3 fail_timeout=30s;
		server 127.0.0.1:8002 weight=2 max_fails=3 fail_timeout=30s;
		# Можно задать вес (мощный сервер получит больше трафика)
		server 192.168.1.10:80 weight=3 max_fails=3 fail_timeout=30s;
		server 192.168.1.11:80 backup; # Резервный, отправляются запросы, только если основные упали
	}
}

Server (Виртуальный хост)

Описывает настройки для конкретного домена. Может быть разделение по номеру порта (каждый Server слушает свой порт) и/или по заголовку в запросе Host при работе на одном порту.

# 1. MAIN CONTEX
worker_processes auto;
...
http {
    # 3. HTTP CONTEXT
    include mime.types;
    ...
    # 4. SERVER CONTEXT (VHost 1)
    server {
        listen 80; # Запросы на какой порт относятся к данному Server
        listen [::]:80; # Для поддержки IPv6
        server_name site1.com www.site1.com ; # Какие записи в заголовке запроса Host относятся к данному Server
        return 301 https://$host$request_uri; # Отправить на любой запрос ответ с кодом 301 и URL для перенаправление (в заголовке Location) на 443 порт
    }

	server {
        listen 443 ssl;
        server_name site1.com www.site1.com ;
		error_page  404 /error404.html; # Какую страницу использовать при ошибке
        ...
    }

	# 4. SERVER CONTEXT (VHost 2)
    server {
        listen 443 ssl;
        server_name site2;
        ...
        location / {
            ...
        }
    }

    # 4. SERVER CONTEXT (VHost 3)
    server {
        listen 8081;
        server_name _;
        ...
    }
}

Location (Локация)

Правила обработки конкретных URI (путей). Самая частая зона для настройки. Распологается внутри server { ... }

# 1. MAIN CONTEXT
worker_processes     auto;
...    
http {
    # 3. HTTP CONTEXT
    ...
    # 4. SERVER CONTEXT 
    server {
		error_page  404 /error404.html; # Какую страницу использовать при ошибке
        ...
		# 5. LOCATION CONTEXT
		location /error404.html { # Точное совпадение URI
			internal; # Указывает, что данный URI является внутренним (служебным)
			expires -1; # время кеширования
			add_header "Content-Security-Policy" "$csp_header" always; # добавляем заголовок к ответу
			root      /var/lib/ecp-veil/utils/other/nginx-error-page; # путь к файлам (склеивается с URI)
			index     error404.html; # список файлов, которые сервер будет искать и отдавать по умолчанию
			sub_filter 'NG_CSP_NONCE' $csp_nonce; # Поменять в теле ответа строку 'NG_CSP_NONCE' на значение переменной $csp_nonce
			sub_filter_once off; # не останавливаться при замене в теле после нахождения первого вхождения
		}
		location ^~ /img/ { # префиксное совпадение останавливает поиск regex.
			alias /var/www/static/; # подмена пути (URI /img/ -> /var/www/static/).
			try_files $uri $uri/ =404; # проверка существования файла. Если нет файла отдать ошибку 404
			...
		}

		location ~ \.php$ { #  регулярное выражение (чувствительно к регистру).
			...
		}
		location ~* \.png$ { # регулярное выражение (без учета регистра).
			...
		}
		location /api/ { # префиксное совпадение (самый низкий приоритет).
			proxy_pass http://localhost:8000; # проксирование на бэкенд.
			...
		}
    }
}

Иерархия директорий Nginx в Linux

Понимание структуры каталогов Nginx критически важно для администрирования, отладки и обеспечения безопасности сервера. В Linux-системах (Debian/Ubuntu, CentOS/RHEL) структура следует стандартам FHS (Filesystem Hierarchy Standard).
  • /etc/nginx/nginx.conf - Главный конфигурационный файл. Содержит глобальные настройки и подключает остальные файлы через директиву include.
  • /etc/nginx/sites-available/ - Хранилище конфигураций виртуальных хостов (Server Blocks). Файлы в этой директории не активны. Nginx их игнорирует, пока на них нет ссылки.
  • /etc/nginx/sites-enabled/ - Директория «активных» сайтов. Чтобы включить сайт, создается символическая ссылка (symlink) из sites-available в sites-enabled.

Обратный прокси (Reverse Proxy) и балансировка нагрузки

Это самое частое применение. Nginx стоит «спереди» (как входная дверь) и распределяет трафик между несколькими бэкенд-серверами (Node.js, Python, PHP-FPM). Или проксирует соединяния в зависимости от заголовка запроса Host (размещение нескольких сайтов на одном IP адресе)

http {
    # 3. HTTP CONTEXT
    ...
	# 1. Объявляем группу серверов (upstream)
	upstream backend_pool {
		least_conn; # Nginx отправляет запрос на тот сервер, у которого сейчас меньше всего активных соединений.
		server 192.168.1.9:80 weight=2 max_fails=3 fail_timeout=30s;
		server 192.168.1.10:80 weight=3 max_fails=3 fail_timeout=30s;
		server 192.168.1.11:80 backup; # Резервный, отправляются запросы, только если основные упали
	}

	# 2. Настройка виртуального хоста
	server {
		listen 80;
		server_name example.com;

		location / {
			# Проксируем всё в нашу группу
			proxy_pass http://backend_pool;

			# Критически важные заголовки:
			proxy_set_header Host $host;
			proxy_set_header X-Real-IP $remote_addr;
			proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
			proxy_set_header X-Forwarded-Proto $scheme;
		}
	}
}

Отдача статического контента

Nginx невероятно быстр в отдаче файлов (картинки, CSS, JS, HTML).

http {
    # 3. HTTP CONTEXT
    ...
	# 2. Настройка виртуального хоста
	server {
		listen 80;
		server_name example.com;

		location /static/ {
			alias /var/www/project/static/;
			expires 30d; # Кэшируем в браузере на 30 дней
			add_header Cache-Control "public";
			access_log off; # Не пишем логи для статики
		}
	}
}

Кэширование (Micro-caching)

Nginx может сам сохранять ответы бэкенда в памяти или на диск. Это спасает при «пиках» нагрузки (например, публикация новости), когда тысячи людей одновременно запрашивают одну и ту же страницу.

http {
    # 3. HTTP CONTEXT
	proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m inactive=60m;
	...
	server {
		location / {
			proxy_cache my_cache;
			proxy_cache_valid 200 60s; # Кэшируем успешные ответы на 1 минуту
			proxy_pass http://backend;
		}
	}
}

API Gateway (Входная точка для микросервисов)

Когда у вас много микросервисов, Nginx выступает единой точкой входа, маршрутизируя запросы по URL.

http {
    # 3. HTTP CONTEXT
	...
	server {
		location /api/users/ {
			proxy_pass http://users-service:8000;
		}
		location /api/orders/ {
			proxy_pass http://orders-service:8001;
		}
		location /api/payments/ {
			proxy_pass http://payments-service:8002;
		}
	}
}

API Gateway (Входная точка для микросервисов)

Когда у вас много микросервисов, Nginx выступает единой точкой входа, маршрутизируя запросы по URL.

http {
    # 3. HTTP CONTEXT
	# Зона лимита: 1 запрос в секунду, burst до 5
	limit_req_zone $binary_remote_addr zone=api_limit:10m rate=1r/s;
	...
	server {
		location /api/login {
			limit_req zone=api_limit burst=5 nodelay;
			proxy_pass http://backend;
		}
	}
}
